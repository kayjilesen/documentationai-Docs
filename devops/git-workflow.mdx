## Overzicht

Elk project is een Git repository. De workflow is eenvoudig: werk op de `main` branch, commit regelmatig, en push naar de remote.

---

## Basis Workflow

<Steps>
  <Step title="Pull laatste wijzigingen" icon="download">
    ```bash
    git pull origin main
    ```
  </Step>
  <Step title="Ontwikkel" icon="code">
    Maak wijzigingen aan PHP, CSS, JS bestanden. Draai `npm run dev` voor Tailwind watch.
  </Step>
  <Step title="Build assets" icon="terminal">
    ```bash
    npm run build
    ```

    Dit compileert CSS en bundelt JavaScript. **Altijd builden voor een commit.**
  </Step>
  <Step title="Review en commit" icon="git-branch">
    ```bash
    git status          # Bekijk gewijzigde bestanden
    git diff            # Review wijzigingen
    git add .           # Stage alles
    git commit -m "Add hero block met responsive layout"
    ```
  </Step>
  <Step title="Push" icon="upload">
    ```bash
    git push origin main
    ```
  </Step>
</Steps>

## Commit Conventies

| Prefix | Gebruik | Voorbeeld |
|--------|---------|-----------|
| `Add` | Nieuwe feature of block | `Add team block with ACF fields` |
| `Update` | Wijziging aan bestaand | `Update hero block responsive spacing` |
| `Fix` | Bug fix | `Fix button hover state on mobile` |
| `Refactor` | Code herstructurering | `Refactor pagebuilder loop logic` |
| `Improve` | Visuele/UX verbetering | `Improve contact form validation` |
| `Remove` | Verwijdering | `Remove unused CSS imports` |

**Regels:**
- Begin met een werkwoord in de tegenwoordige tijd
- Beschrijf WAT er veranderd is, niet HOE
- Maximaal 1-2 regels
- Engels

## Code Quality Tools

Sommige projecten hebben ESLint en Husky geconfigureerd voor automatische code quality checks:

### ESLint

```bash
# Lint controleren
npm run lint:js

# Automatisch fixen
npm run lint:js:fix
```

### Husky + lint-staged

Bij projecten met Husky draait er automatisch een **pre-commit hook** die ESLint uitvoert op gewijzigde `.js` bestanden:

```json
// package.json
"lint-staged": {
    "*.js": "eslint --no-warn-ignored"
}
```

Als linting faalt, wordt de commit geblokkeerd. Fix de issues en probeer opnieuw.

<Callout kind="tip" title="Husky installeren">
  Na een `npm install` op een project met Husky wordt de hook automatisch geïnstalleerd via het `prepare` script.
</Callout>

## .gitignore

Standaard genegeerde bestanden:

```
node_modules/
.DS_Store
```

**Wel committen:**
- `assets/css/style.css` (gecompileerde CSS)
- `assets/js/pagebuilder.js` (gebundeld JS)
- `acf-json/` (ACF veldgroepen)

**Niet committen:**
- `wp-config.php`, de database, `wp-content/uploads/` en plugins — de repo bevat alleen de themamap
- `.env` en `.mcp.json` — hierin staan wachtwoorden of sleutels in platte tekst
- `debug.log` en andere logbestanden

<Callout kind="warning" title="Waar het misgaat">
  - **Git gestart in de hele WordPress-map** in plaats van in de themamap: dan staan core, uploads en `wp-config.php` straks in je repo. Open alleen de themamap en start daar.
  - **`.gitignore` verwijdert niets** wat al gevolgd wordt. Staat een bestand er al in, haal het dan eerst uit Git (`git rm --cached`).
  - **Een wachtwoord dat één keer gecommit is, blijft in de geschiedenis staan**, ook als je het later weghaalt. Vervang dan het wachtwoord zelf.
</Callout>

## Opleveren in de repo

Aan het eind van een fase en bij de definitieve oplevering moet iemand anders met de repo verder kunnen.

<Steps>
  <Step title="Controleer wat erin zit" icon="search">
    `git status` en `git diff`: alleen de bedoelde bestanden, geen geheimen of logbestanden. Zo gaat er geen wachtwoord of half werkbestand mee naar GitHub.
  </Step>
  <Step title="README bijwerken" icon="file-text">
    Zet erin wat nodig is om te starten: benodigde plugins, build-commando's en de mappenstructuur. Een README die naar commando's verwijst die niet meer bestaan is erger dan geen README.
  </Step>
  <Step title="Alles meenemen wat bij de code hoort" icon="package">
    ACF-JSON, bronbestanden, `package-lock.json` en de gebouwde CSS/JS (zie "Wel committen"). Zonder de nieuwste JSON of build ziet de volgende omgeving iets anders dan jij.
  </Step>
  <Step title="Build draaien en testen" icon="terminal">
    `npm run build`, daarna de site, het `debug.log` en de browserconsole nalopen — zie [Configuratie](/wordpress/configuratie).
  </Step>
  <Step title="Pushen en nakijken op GitHub" icon="upload">
    Een lokale commit is nog niet gedeeld. Kijk op GitHub of de laatste commit er staat en of de ander toegang heeft tot de repo.
  </Step>
</Steps>

## Tips

- Commit regelmatig — liever veel kleine commits dan één grote
- Build altijd voor een commit (`npm run build`)
- Review je `git diff` voor je commit — voorkom ongewenste wijzigingen
- ACF JSON bestanden: controleer dat de `"modified"` timestamp is bijgewerkt
